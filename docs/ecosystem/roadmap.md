# Cedarflake Ecosystem · 产品、共享架构与完整路线图

**文档版本：** 0.2  
**更新日期：** 2026-11-16  
**文档性质：** Cedarflake 软件家族的产品规划、工程架构与分阶段交付规范  
**适用项目：** Cedarflake Ame、Cedarflake Oboro、Cedarflake Shizuku、Cedarflake Foundation

> **总目标：** Ame 负责图片整理，Oboro 负责视频整理与轻量剪辑，Shizuku 负责音频整理。三个应用独立安装、独立运行、独立发布；Cedarflake Foundation 提供共享 Flutter Material 3 前端组件和 Rust 基础设施。各应用拥有自己的媒体处理、业务数据和操作流程。

## 1. 产品版图与现状

| 项目 | 名称 | 产品定位 | 当前进度 |
| --- | --- | --- | --- |
| Cedarflake Ame | 雨（Ame） | 大型本地图片库、精确及相似去重、智能分类、语义检索、文件整理 | R0–R9 主要功能已交付；R10 正在进行 Beta 发布准备 |
| Cedarflake Oboro | 朧（Oboro） | 视频图库、视频去重、非破坏性轻量剪辑、多轨音频 | 产品路线图已规划，尚未开始实现 |
| Cedarflake Shizuku | 雫（Shizuku） | 音乐、录音、音效与配音素材整理，音频去重、元数据和基础编辑 | 产品路线图已规划，尚未开始实现 |
| Cedarflake Foundation | 共享基础设施 | Flutter UI 组件库、Rust 文件与任务能力、媒体接口和平台适配 | 规划抽离；现有可复用实现主要位于 Ame |

### 1.1 项目之间的关系

- **Ame** 管理图片，不增加视频和音频图库，也不成为多媒体编辑器。
- **Oboro** 管理视频，提供视频剪辑及音轨操作；它不取代专门的音频资料库。
- **Shizuku** 管理音频，包括歌曲、录音、音效和配音；基础音频处理不扩展为完整 DAW。
- **Foundation** 负责稳定的公共能力，不直接提供终端用户产品，也不持有三个应用的业务数据库。
- 三款应用可以独立使用。互通功能通过文件、明确的导入导出操作和版本化协议实现。

### 1.2 规划与交付的区分

使用三个固定状态：**已交付、进行中、规划中**。Ame 的状态以其仓库 `docs/roadmap.md` 为准；本文件保留其阶段原名和历史记录。Oboro、Shizuku、Foundation 的 R0–R10 是各自独立的交付序列。

**阶段标识使用完整项目名前缀**，例如 `Oboro/R3`、`Shizuku/R3`、`Foundation/R3`。同名阶段之间无隐式依赖，依赖须在对应阶段列明。

## 2. 共同产品与工程原则

1. **本地优先**：离线可浏览、搜索、播放和整理本地媒体；在线元数据识别是可选增强。
2. **源文件优先保护**：扫描、索引、分析、预览、收藏和虚拟分类保持只读；物理文件变更使用明确的授权和复验流程。
3. **身份、位置、证据、决策分离**：逻辑资源身份、物理文件位置、精确指纹、相似候选和用户偏好分别保存。
4. **可扩展的大型库**：增量变化处理、有限内存、按需读取、可取消后台任务、可恢复进度。
5. **统一的交互体系**：三款应用使用相同的 Material 3 组件规范、设计令牌、动效语义、键盘规则及可访问性要求；业务界面根据图片、视频、音频各自的操作需要组织。
6. **复用成熟技术**：优先接入成熟编解码、元数据、指纹和时间轴引擎，减少自行维护底层算法的范围。
7. **独立数据与发布**：每款应用自己的配置、数据库、迁移、缓存及版本；Foundation 采用独立包版本。
8. **Windows 11 x64 优先**：延续 Ame 已经验证的 Flutter + Rust 技术路线；平台相关能力通过适配层隔离。
9. **单一事实来源**：每个仓库的 `docs/roadmap.md` 管理进度，产品规范管理行为，ADR 管理技术决策，验收文档保存实测证据。

### 3.1 依赖规则

```text
Ame ────────┐
Oboro ──────┼──> Foundation 的公开、版本化接口 ──> 第三方依赖/操作系统
Shizuku ───┘

Foundation 不能依赖任何应用的业务层。
应用不能直接导入其他应用的内部源码或数据库。
```

- Flutter 层负责渲染、交互、焦点、动画与用户意图提交。
- Rust 层负责目录与文件访问、索引、任务、持久化和媒体分析。
- `flutter_rust_bridge` 由每个应用独立生成和维护；公共 Rust 类型不依赖生成桥接类型。
- 资源读写经过明确端口，由具体 Windows 适配器实现。业务策略由调用的应用决定。
- 共享包各自包含 API 文档、最小使用示例、版本说明和相应的契约测试。

## 4. Foundation 的模块设计

### 4.1 `cedarflake_ui`：Flutter 共享前端

**首批抽离范围（以 Ame 已有实现为起点）：**

| 模块 | 共享内容 | Ame 中的起点 |
| --- | --- | --- |
| Theme & Tokens | Material 3、系统动态配色、排版、间距、形状、状态层 | Ame 全局主题及公共 presentation 代码 |
| Motion | Spring 与时长令牌、正反向切换、取消、减少动画偏好 | `ame_motion.dart` 与交互协调实现 |
| Dialog | 对话框容器、滚动、表单、失败提示、操作确认 | `ame_dialog.dart` |
| Progress | 延迟呈现、进行中/完成态、线性与圆形进度、语义标签 | `ame_progress.dart` |
| Loading | Material Expressive 加载控件 | `ame_loading_indicator.dart` |
| Desktop Controls | 快捷键、菜单、路径展示、工具提示、焦点、选择反馈 | 经抽离审计后纳入 |
| Notifications | 通用通知结构、展示与关闭交互 | 仅提取与 Ame 业务无关的部分 |
| Accessibility | 键盘导航、焦点顺序、高对比度、减少动态效果 | 通用交互契约 |

`AmeLoadingIndicator` 当前包含改编自 Flutter 上游代码的实现；提取时保留 BSD-3-Clause 署名、许可文本及来源记录。如果上游提供正式组件，优先评估替换。

**归属原则：**

- 公共包拥有通用呈现与输入规则。
- Ame 的图片墙、滚动锚点和图片查看器保留在 Ame。
- Oboro 的剪辑时间轴、视频播放器交互留在 Oboro。
- Shizuku 的波形编辑器、专辑浏览交互留在 Shizuku。
- 三款应用默认使用同一套设计规范；独立页面布局由业务决定，不引入三套产品专属的视觉系统。

### 4.2 `cedarflake_filesystem`：安全文件访问

职责：文件身份识别、路径和来源状态复验、文件访问租约、Windows 文件系统适配、变化事件的规范化，以及底层文件操作执行。

主要接口候选：

- `SourceHandle` / `SourceLease`：已核准文件的受保护读取，附带明确释放语义。
- `FileIdentity` / `SourceVersion`：文件身份与版本证据，独立于绝对路径。
- `ChangeEvent`：新增、修改、移动、删除和未知状态统一表达。
- `OperationReceipt`：物理操作真实结果、目标身份及可恢复信息。
- `SourceAvailability`：本地、不可用、云占位、权限阻断等状态。

Windows 适配保留当前文件句柄、NTFS 变化、路径重解析、云占位和回收站处理中的可靠行为。目录扫描与后台同步的具体节奏由上层任务策略决定。

**授权边界**：Foundation 执行已核准的操作；每个应用负责决定操作目标、冲突策略、对话确认、操作日志及业务数据库更新。文件路径或来自另一应用的消息本身不构成修改授权。

### 4.3 `cedarflake_fingerprint`：精确指纹

职责：基于 `Read`/流的 BLAKE3 内容哈希、长度验证、取消、结果格式和算法版本。库不负责任意路径打开、图库范围选择或用户删除决定。

- 精确重复依据：**完整文件长度 + 完整内容指纹 + 兼容的算法版本**。
- 局部哈希可以筛选候选，但不作为“完全重复”的最终依据。
- 支持有限大小缓冲读取和长任务取消；上限属于应用策略。
- Ame 现有 256 MiB 原文件读取上限由 Ame 保留；Oboro 按 GB 级视频设置独立预算。
- 同内容多文件位置保留独立位置身份；硬链接与跨卷副本分别处理。
- 已确认指纹可以缓存；文件身份、版本或来源状态变化会触发正确失效。

### 4.4 `cedarflake_tasks`：后台任务与资源调度

职责：任务生命周期、前台优先、取消、暂停、进度事件、资源额度和错误传播。

- 大规模索引和分析任务分批提交，避免一次占满内存。
- 用户当前播放、查看和交互读取具有优先级。
- 视频解码、音频播放、哈希和导出由各自任务类型申请资源额度。
- 任务执行结果与 UI 呈现状态分开；完成提示以已提交的结果为准。
- 异常、取消、关闭程序和重启后恢复的语义明确记录。

### 4.5 `cedarflake_persistence`：持久化组件

可共享：SQLite 连接管理、事务辅助、分页游标技术、迁移运行器、错误类型、测试夹具。

每款应用独立拥有：业务表结构、Schema 版本、索引策略、配置、相册/标签/工程文件、用户决策、数据库升级与恢复流程。Ame 现有数据库不迁移为三应用共用数据库。

### 4.6 `cedarflake_media_contracts`：媒体能力接口

| 通用端口 | Ame 的实现 | Oboro 的实现 | Shizuku 的实现 |
| --- | --- | --- | --- |
| `MediaProbe` | 图片格式、尺寸、EXIF | 容器、视频/音频流、帧率和时长 | 编码、时长、采样率与标签 |
| `MediaPreview` | 图片缩略图 | 关键帧与预览序列 | 封面和波形 |
| `MediaAnalysis` | 图像感知指纹、AI 向量 | 视频指纹、时间片段特征 | 音频指纹、声音特征 |
| `MediaSource` | 图片解码读取 | 音视频解码与定位 | 音频解码与试听 |
| `MediaExport` | 既有文件/图片导出 | 封装、转码、工程渲染 | 音频转换、片段导出 |

这里只共享契约和必要的值类型。格式识别、编解码、缓存刷新与分析算法放在媒体专属适配器中。

### 4.7 `cedarflake_interop`：应用互通

第一版使用标准文件、导出路径和 OS 文件关联，之后按实际场景加入带版本的应用间请求。

- `Oboro → Shizuku`：导出音轨，发送到音频库。
- `Shizuku → Oboro`：从音频库选择音乐或音效，添加到剪辑工程。
- `Oboro → Ame`：截取视频帧，保存为图片并导入 Ame。
- `Ame → Oboro`：提供静态图片作为封面、片头或时间轴素材。

交接格式记录来源、动作、媒体文件引用和协议版本。接收方重新检查文件状态；缺少另一款应用时仍可保存文件或使用系统默认程序打开。

## 5. 统一路线图规范：各项目独立 R0–R10

每个项目在自己的 `docs/roadmap.md` 中使用相同的记录结构：

1. **Product direction**：用户需求、范围和排除项。
2. **Delivery sequence**：R0–R10 的阶段名称、目标和状态。
3. **Current stage and acceptance boundary**：当前阶段、已完成证据与阻断项。
4. **Current execution queue**：有序的下一批实现工作。
5. **Stage plans**：每个阶段明确的子任务与依赖，例如 `R9-01`、`R9-02`。
6. **Exit conditions**：功能、数据安全、性能、兼容性、平台测试与文档的完成条件。
7. **Integration evidence**：PR、代码修订、构建和实际设备结果。

**R10 统一作为发布就绪阶段**，包含资源边界、升级兼容、诊断、打包和发布。正式版后的新增能力另设版本路线图，不改写已交付的 R0–R10 历史。

## 7. Foundation 路线图：R0–R10

**产品目标：** 将 Ame 中已经稳定的通用能力演进为可独立使用、独立测试、独立版本化的 Flutter/Rust 包，供三款应用复用。

| 阶段 | 交付目标 | 依赖与主要验收 |
| --- | --- | --- |
| **R0 基线与契约** | 现有代码依赖审计、API 候选清单、资源所有权、许可与行为基线 | 建立完整可追溯的候选清单；Ame 运行与数据保持原状 |
| **R1 UI 设计系统** | 共享 Material 3 主题、令牌、加载、进度与对话框 | 独立示例应用可运行；Ame 的交互与视觉回归通过 |
| **R2 桌面交互组件** | 通用菜单、快捷键、焦点、通知和桌面窗口组件 | 键鼠、无障碍和减少动态效果行为可验证 |
| **R3 精确内容指纹** | BLAKE3 流式计算、哈希证据版本、兼容缓存接口 | 与 Ame 旧结果一致；大文件任务有界并可取消 |
| **R4 安全来源读取** | 文件身份、来源版本、受保护读取租约、Windows 平台适配 | 跨路径重解析、占位文件和源变更校验正确 |
| **R5 索引与持久化基础** | 可组合的变更事件、分页查询辅助、SQLite 迁移组件 | 独立消费者运行，应用数据表仍由各自拥有 |
| **R6 任务与资源调度** | 任务优先级、取消、暂停、结果发布和资源预算 | 多任务压力下前台操作稳定，关闭后资源正确释放 |
| **R7 媒体处理契约** | 元数据、预览、播放读取、相似特征与导出接口 | 图片/视频/音频各有独立适配器示例，类型边界清楚 |
| **R8 文件操作执行器** | 复制、移动、重命名、删除、结果凭据和错误恢复底层接口 | Windows Sandbox 中验证身份复验、冲突与中断恢复 |
| **R9 应用互通合同** | 文件交接、可选 IPC、协议版本与接收方校验 | 不安装其他应用时仍正常；跨应用动作保留来源授权 |
| **R10 独立发行与兼容** | 包版本、API 稳定级别、Changelog、构建/许可/升级验收 | 示例消费者与各已接入应用通过发布门禁 |

### Foundation/R0：基线与依赖审计

交付：模块使用图、通用/产品专属分类、提取候选排序、API 清单、基线运行结果、数据库与源文件安全约束。

| 元数据 | 读取契约 | EXIF/图片属性 | 视频容器/流信息 | 音频标签/封面 |
| 虚拟整理 | 通用交互组件 | 相册/收藏/智能相册 | 合集/标签/收藏 | 专辑/队列/标签/收藏 |
| 文件更改执行 | Windows 适配与凭据 | 图片授权与图库更新 | 视频授权与图库更新 | 音频授权与资料库更新 |
| AI/语义搜索 | 通用任务与端口 | 图片模型与语义特征 | 视频扩展实现 | 音频扩展实现 |
| 剪辑/编辑 | 媒体处理接口 | 保留原产品范围 | 视频时间轴与多音轨 | 基础音频编辑 |
| 桌面 UI | 组件与令牌 | 图片工作台 | 视频工作台 | 音频工作台 |

## 11. 从 Ame 抽离共享能力的实施顺序

这条路线与 Foundation R0–R10 对应。**阶段按照 R0→R10 顺序管理；每次抽离都先让 Ame 使用新包并验证，再继续下一阶段。** 对第二、第三款应用暂时用不到的能力，阶段可以保持在规划状态，不在 Ame 中预先做大规模重构。

| 实施批次 | 对应阶段 | 工作 | 验收与回退 |
| --- | --- | --- | --- |
| 1 | Foundation/R0 | 记录公共候选、依赖链、许可和行为基线 | 不改应用代码；产出模块审计与接口草案 |
| 2 | Foundation/R1 | 提取主题、进度、加载、对话框 | Ame 原界面行为一致；旧实现可恢复 |
| 3 | Foundation/R2 | 提取确属通用的菜单、快捷键和桌面交互 | 交互、焦点、快捷键验证通过 |
| 4 | Foundation/R3 | 独立提取纯 BLAKE3 哈希计算 | 字节结果与现有实现一致，原数据库无需迁移 |
| 5 | Foundation/R4 | 提取受保护来源读取与 Windows 文件身份机制 | 源身份、版本、权限、占位文件与资源释放行为稳定 |
| 6 | Foundation/R5 | 提取通用事件/持久化技术组件 | 不改变 Ame Schema 或业务接口 |
| 7 | Foundation/R6 | 根据真实任务类型抽离调度机制 | 前台优先、取消与生命周期验证通过 |
| 8 | Foundation/R7 | 收敛媒体探测/预览/分析的共用端口 | 至少两个不同媒体适配器使用稳定接口 |
| 9 | Foundation/R8 | 单独迁移 Windows 物理操作执行器 | 沙箱验证复制、移动、删除、恢复 |
| 10 | Foundation/R9–R10 | 应用互通、公共包发布和兼容策略 | 各程序独立构建、升级、回退 |

### 11.1 优先保留的 Ame 专属能力

- 图库完整结果集查询、时间轴与连续滚动锚点。
- 图片查看器、全分辨率读取、图片预览与缓存策略。
- 分类模型、图片相似组、图片搜索与模型输出。
- 用户相册与图库的具体业务规则。
- Ame 当前数据库及迁移历史。
- Ame 的 UI 页面、业务通知文案和已完成的交互决定。

### 11.2 可先独立发布的最小公共包

**第一批：** `cedarflake_ui` 和 `cedarflake_fingerprint`。两者既有来自 Ame 的真实实现，也比较容易以清晰接口提供给未来应用。

**第二批：** 文件来源读取、任务调度和存储技术组件。它们涉及 Ame 已建立的资源所有权与多层状态一致性，应结合第二个应用的真实消费场景逐步抽离。

### 11.3 应用依赖与示例验证

每个公共包必须附带至少一个不依赖 Ame 源码的示例消费者。Ame 切换到提取后的包时，保持其版本化契约、生成桥接代码边界、现有测试与运行行为。


- Foundation 的 Rust crate 与 Flutter package 分别版本化。各应用固定已验证的依赖版本。
- 公共 API 的不兼容变更记录在 Changelog/ADR，并提供清晰迁移路径。

- 自有公共代码沿用 Apache-2.0 作为目标许可；第三方引擎和上游组件按实际构建、链接与分发方式执行许可证审核。

## 13. 关键技术选型与复用范围

| 功能 | 优先评估方案 | 评估内容 |
| --- | --- | --- |
| Flutter 设计系统 | `material_ui` 与 Ame 已采用的 Material 3 实现 | SDK 兼容、组件行为、无障碍与后续升级成本 |
| 精确去重 | Ame 已使用的 BLAKE3 | 大文件性能、取消、缓存失效、读写安全 |
| 图片相似 | Ame 现有 `image_hasher` 与图像分析链 | 维持 Ame 当前结果和证据兼容 |
| 视频容器/解码/导出 | FFmpeg、Windows Media Foundation | Windows 接入、硬件解码、格式支持、许可证与安装体积 |
| 视频剪辑时间轴 | MLT Framework | 多轨、音频混合、预览导出一致、Rust/Flutter 集成 |
| 视频相似 | 多帧采样、感知指纹及现成算法库 | 不同编码/分辨率、裁剪、水印、片段重合的质量 |
| 音频指纹 | Chromaprint / AcoustID 技术栈 | 声学重复质量、不同母带误判、离线能力 |
| 音乐元数据 | 本地标签解析器、可选 MusicBrainz | 多格式读写、封面、隐私和冲突解决 |
| 数据库 | SQLite 与各应用自有 Schema | 查询性能、增量索引和升级兼容 |

成熟引擎采用**候选评估 → 固定语料测试 → Windows 集成 → 许可核查 → 版本锁定**的过程。对 FFmpeg、MLT 等项目，按实际启用模块处理 LGPL/GPL 及附加许可证要求。

## 14. 质量门禁与验收体系

### 14.1 通用必测行为

| 门禁 | 要求 |
| --- | --- |
| 来源保护 | 只读操作无源文件写入；所有物理更改有明确授权 |
| 结果证据 | 完整哈希、感知候选、用户决定严格区分 |
| 身份与变化 | 移动、重命名、替换、删除、离线、占位文件正确处理 |
| 数据兼容 | 升级保留已有图库、收藏、相册、标签、工程及用户决定 |
| 资源约束 | 大图库、长视频、大文件、波形构建均有界且可取消 |
| UI 连续性 | 可见窗口稳定、进度符合真实任务状态、焦点与键盘可用 |
| 崩溃与恢复 | 中断后任务与文件操作结果可解释，已提交内容不会丢失 |
| 发布质量 | 构建/打包、依赖许可证、版本兼容、诊断和安装卸载验收 |

### 14.2 按项目增加的验收

**Ame：** 图片预览质量、相似组稳定、语义搜索、时间轴锚点、真实大图库与升级回归。

**Oboro：** 视频 seek 精度、软硬件解码回退、时长/关键帧正确性、大文件哈希、视频相似误判、多轨同步、工程重开、预览与最终导出一致。

**Shizuku：** 各格式标签读取与写回、专辑封面、声学指纹误判、音频播放稳定、波形选区和导出长度、批量归档恢复。

**Foundation：** 独立消费者接口、平台能力隔离、Ame 行为一致、包版本兼容和 Windows 文件操作沙箱测试。

### 14.3 测试与 CI 分层

- **快速门禁**：格式化、静态分析、受影响的 Rust 单元与 Flutter Widget/应用测试。
- **完整门禁**：共享契约、桥接、应用核心集成测试和 Windows 构建。
- **平台门禁**：文件身份、占位文件、跨卷移动、回收站、安装与升级。
- **性能门禁**：真实规模或可重复合成语料的延迟、内存、CPU、IO 和操作流畅性。
- **发布门禁**：发布工件、许可证、版本、迁移和异常恢复。

沿用 Ame 已经建立的按影响范围选择测试的机制；完成的有效验收可以继续复用，新增行为增加对应验证。

## 15. 开发顺序与长期演进

### 15.1 当前顺序

1. **完成 Ame/R10**：收尾大型图库可靠性、升级兼容、诊断及 Beta 交付。
2. **实施 Foundation/R0**：梳理现有模块和共享 API，记录已验证的基线。
3. **实施 Foundation/R1–R3**：优先提取共享 UI 和纯哈希计算。
4. **维护 Oboro、Shizuku 的 R0–R10 产品规范**：继续使用现有媒体工具，逐步收集真实使用场景和测试语料。
5. **出现实际第二消费者时推进 Foundation/R4–R9**：利用具体集成反馈完善共享接口，再启动相应应用阶段。

### 15.2 里程碑之间的依赖

- Foundation/R1 可以在 Oboro、Shizuku 开发之前交付。
- Foundation/R3 的纯哈希库可以在 Ame 内完成验证，GB 级视频策略由 Oboro/R3 负责。
- Oboro/R1、Shizuku/R1 可在应用自有适配器内先实现，Foundation/R4/R5 再抽取重复且稳定的部分。
- Oboro/R9 的剪辑引擎不加入 Foundation；仅共享必要的媒体读取和导出接口。
- Shizuku/R6 的声学指纹不要求 Ame 修改其图片相似架构。
- Foundation/R9 依赖至少两款可实际交互的应用。

### 15.3 新产品启动条件

Oboro 的启动依据是现有视频管理/轻剪辑工作流出现持续性缺口，例如视频版本查重与剪辑无法自然衔接。Shizuku 的启动依据是本地音乐、录音或音效资料库达到需要批量整理、声学去重和元数据管理的规模。两个产品可以分别启动，互不等待。

## 16. 风险与对应技术决策

| 风险 | 处理方式 |
| --- | --- |
| Foundation 包含 Ame 专属业务 | 按可证明的职责划分端口；保留每个应用自己的领域与数据库 |
| 迁移导致 Ame 回归 | 每个组件独立迁移，保持原行为基线和可回退路径 |
| 三款应用被共同版本绑死 | 公共包独立版本，应用锁定兼容版本 |
| 视频哈希耗时和 IO 争用 | 大文件流式读取、优先级与取消，独立资源预算 |
| 视频相似候选误判 | 固定语料、时间范围证据、人工复核和候选独立呈现 |
| 音频同曲不同版本被误清理 | 声学相似和字节重复明确分离，质量差异可见 |
| 视频编辑器范围无限扩张 | R9 专注剪切、拼接、多轨音频、基础效果和可靠导出 |
| Windows 文件操作导致数据损坏 | 受保护句柄、来源复验、授权、操作凭据及沙箱验收 |
| 上游引擎许可与维护成本 | 编译模块、链接方式、打包、许可证和升级策略逐项审核 |
| 公共框架复杂度过高 | 以实际消费者为准逐步抽离，未使用接口保持在规划层 |

## 17. 决策记录与文档维护

**现有决定：**

- 三款应用独立，Foundation 共享稳定技术组件。
- 三款应用使用共同的 Flutter Material 3 设计系统，不建立三套视觉设计语言。
- Ame 保留已有 R0–R10；Foundation、Oboro、Shizuku 分别使用自己的 R0–R10。
- 图片、视频、音频相似识别使用媒体专属算法；精确哈希逻辑统一。
- 视频剪辑与音频编辑均采用优先保留源文件的工作流。
- 文件操作授权与用户决定由各应用拥有。
- Oboro、Shizuku 的产品范围保留；是否开始实现由实际需求与阶段完成条件决定。

**后续 ADR 主题：** Foundation 的包边界、UI 公开接口、Rust 资源租约、媒体引擎选择、视频指纹方案、音频指纹方案、剪辑工程文件格式、跨应用协议以及公共包版本兼容规则。

**文档维护：** 当实现开始后，具体状态、PR 和验收日期写入对应仓库的 `docs/roadmap.md` 与 `docs/acceptance/`。本文件维护跨项目关系、稳定产品范围和阶段依赖。
